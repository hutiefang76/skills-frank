# ADR-014: v0.14 综合架构 — 5 通道统一 + Skill 跨机同步 + MCP 凭证分离

**Status**: Accepted
**Date**: 2026-05-26
**Replaces / extends**: ADR-009 (5 层凭据), ADR-010 (LanceDB), ADR-011 (Hybrid RRF), ADR-013 (machine-bound token)

| # | 用户原话 | 本质 |
|---|---|---|
| 1 | "frank-mem 怎么在 claude 界面里有提示, 已添加到记忆" | 反馈可见性 (memorix 有, frank 缺) |

## 2. 决策 — 单进程 daemon + Engine 单例 + 5 通道辐射

```
┌────────────────────────────────────────────────────────────────┐
│      frank daemon (axum :7780, Tokio runtime, ~30MB RSS)       │
│                                                                │
│  ┌────────────────────────────────────────────────────────┐    │
│  │  Engine (Rust 单例, Arc-shared)                        │    │
│  │  ├─ manifest::Registry (内存, ~50KB)                   │    │
│  │  ├─ state::State (state.json, ~10KB)                   │    │
│  │  ├─ frank-memory (LanceDB 本地 + Qdrant 服务端)        │    │
│  │  ├─ frank-cred (5 层 fallback, keychain etc.)          │    │
│  │  ├─ market::Index (24h ETag disk cache)                │    │
│  │  └─ sync_client (跨机 tenant/skills 同步)              │    │
│  └────────────────────────────────────────────────────────┘    │
│         ▲          ▲          ▲          ▲          ▲          │
│  ┌──────┴───┐ ┌────┴────┐ ┌───┴───┐ ┌────┴────┐ ┌───┴───┐     │
│  │  Web UI  │ │   CLI   │ │ Hooks │ │ mcp-shim│ │frank- │     │
│  │ (HTTP)   │ │(blocking│ │(stdin │ │(stdio   │ │mcp    │     │
│  │ 7780     │ │  REST)  │ │ JSON) │ │ proxy)  │ │server │     │
│  └──────────┘ └─────────┘ └───────┘ └─────────┘ └───────┘     │
└────────────────────────────────────────────────────────────────┘
        │            │           │            │           │
   浏览器面板    终端 / shell   Claude/Codex/  AI 通过      AI 通过
                                Gemini 写到     MCP 调      MCP 调
                                 settings       业务 server  frank.*
                                                            tools
```

**关键决策**:

1. **5 通道共享同一 Engine** — Web UI / CLI / Hook / mcp-shim / frank-mcp 都打 daemon HTTP / Unix socket, daemon 持有唯一 Engine 实例。**不再有"CLI 自己跑一份, Web UI 自己跑一份" 的双状态**。
2. **daemon 是 1 个进程** — Tokio 多任务调度, 不开线程不开子进程 (除了 install 时的 git clone subprocess)。RSS ~30MB, cold start <100ms。
3. **CLI 短命** — `frank list` 跑 `reqwest::blocking::get("http://127.0.0.1:7780/api/skills")` → 立刻退。daemon 不在时 fail 优雅降级 in-process 跑 Engine (offline mode, 现状 P0)。
4. **Hook 通过 stdio JSON-RPC 走 daemon** — Memorix 借鉴: hook 程序 (`frank hook`) stdin 读 Claude 事件, HTTP POST 到 daemon, 拿 reply 再 stdout `additionalContext` 给 Claude。daemon 不在时 in-process 兜底。
5. **mcp-shim 拦截** — 用户原 `command: "python doris.py"` 改成 `command: "frank mcp-shim doris"`, shim 启动 → 查 frank-cred 拿 DSN → setenv → `execvp` 真 MCP server。凭证零暴露。
6. **frank-mcp** — daemon 同时是个 MCP server (stdio + http transport 二选一), 暴露 `frank.add_memory / frank.search_memory / frank.list_skills / frank.tenant_status`。AI 用 `mcp__frank__add_memory` 主动调。

## 3. 6 个痛点逐一答

### 3.1 反馈可见性 — Memorix `additionalContext` 模式

memorix 实现: hook stdout 输出 `{"hookSpecificOutput":{"additionalContext":"[Memorix] saved: ..."}}`, Claude Code 原生渲染为内联系统消息。这是 anthropic hook spec 字段, 不是 memorix 自创。

frank 复用: `crates/frank-cli/src/hook.rs` 已有, 加输出 `additionalContext` 即可。后台静默存的同时, 用户看到一行 `[frank-memory] saved: <title>`。

### 3.2 市场不卡 — 服务端预编译索引 + 24h ETag 缓存

cc-switch 卡的 3 个根因 (实测代码 skill.rs:1922-2207):
- 下整个 GitHub zip (anthropics/skills 几十 MB)
- react-query `staleTime:Infinity` 但没磁盘 persister → 重启丢
- 主线程同步解压 + 递归扫

frank Rust 方案:
- 服务端 `frank-sync-agent` 加 `/market/index.json` 端点, CI nightly 编译 (扫 5-6 个推荐 repo 的 SKILL.md frontmatter), 一份 ~KB 级 JSON
- 客户端 24h ETag cache 落 `~/.frank/cache/market/index.json`, 重启秒开
- 真要装某个时 `frank install <name>` 才走 git clone (现状, 已有缓存层)

完全不踩 cc-switch 的坑, **因为 frank 跟 cc-switch 架构不同 — 我们用 manifest 模型, 不扫 markdown**。

### 3.3 推荐市场来源

主源 6 个:
- `anthropics/skills` (官方)
- `modelcontextprotocol/servers` (MCP 官方)
- `ComposioHQ/awesome-claude-skills` (864 skills)

- `hutiefang76/skills-*` (frank 自家)

弃: mcp.so / glama.ai (cloudflare 反爬, 不开放 API)。

### 3.4 MCP 0 代码可视化

Web UI 加 MCP tab:
- 5 预设按钮 (fetch/time/memory/sequential-thinking/context7) — 一键启用
- 自定义 form: `name / display / command / args[] / env[k=v] / target_platforms[4 checkbox]`
- 提交 → daemon API `POST /api/mcp` → `installer/mcp.rs` 写 4 家配置文件
- 用户全程不看 JSON

### 3.5 凭证分离 — frank mcp-shim 模式

**架构**:
```
old: ~/.claude.json
     mcpServers.doris:
       command: "python doris.py"
       env:  { DORIS_HOST: "...", DORIS_USER: "...", DORIS_PASS: "..." }  ← 明文 !

new: ~/.claude.json
     mcpServers.doris:
       command: "frank mcp-shim doris --profile uat"
       env:  {}  ← 干净
```

`frank mcp-shim doris --profile uat` 内部:
1. 加载 manifest `doris` 的 `credentials` 字段声明 (例 `DORIS_DSN`)
2. 走 frank-cred 5 层 fallback: keychain → env → ~/.frank/credentials/doris.uat.json → ...
3. 解出 DSN, `std::env::set_var("DORIS_DSN", dsn)`
4. `execvp("python", ["doris.py"])` — 真 MCP server 起来读 env

收益:
- 凭证 0 进 `~/.claude.json` (跟 frank-cred 信任链一致)
- 1 个 MCP server 跑多套连接 (profile 切换)
- `frank login mcp doris --profile uat` 跟现有 `frank login provider claude` 同形, 不引新概念
- 跟 MCP 协议**完全兼容** — Claude/Codex 不知道有 shim 这层

`doris-ops` 现状 (实测 master 分支 doris_ops.py): 凭证在 `config.ini` 跟操作脚本同一个 repo, 装到第二台机器要手编 ini。**v0.14 第一个 migration target**。

### 3.6 5 通道协调

| 通道 | 触发 | 谁用 | 例子 |
|---|---|---|---|
| Web UI | `frank ui` 开浏览器 | 人 — 配置 / 看 | 装 MCP, 看记忆 |
| CLI | `frank <cmd>` 终端 | 人 / 脚本 | `frank list`, CI 用 |
| Slash | `/frank:ask:claude ...` | AI (在 Claude/Codex 聊天里) | 转发问 claude |
| Hook | PostToolUse 自动 | AI 不知道 | mcp__memory__* → 静默落 frank-memory + 反馈 |
| MCP-shim | AI 调 mcp__<X> tool | AI 主动用 MCP server | doris query, 凭证自动注入 |
| frank-mcp | AI 调 mcp__frank__* tool | AI 主动用 frank 能力 | frank.search_memory("rust async") |

**统一靠 Engine 单例**: 5 个通道任何一个改了状态 (装 skill / 加记忆 / 配 MCP), 其他通道立刻看到。例: Web UI 装个 MCP → daemon engine 内存更新 + 写 4 家配置文件 + 通知所有 WS 客户端刷新。

## 5. 性能契约 (justification for Rust)

| 指标 | 上限 | 备注 |
|---|---|---|
| daemon cold start | < 100 ms | Rust + Tokio, 不读模型 |
| daemon RSS idle | < 50 MB | 不 load LanceDB Arrow batches (lazy) |
| `frank list` 响应 | < 50 ms | 走 daemon API, 内存 hit |
| MCP shim spawn | < 20 ms | 走 frank-cred 5 层最长 30ms |
| Hook stdin → stdout | < 100 ms | 不阻塞 Claude 主流程 |
| market index 首次 | < 500 ms | 拉 1 个服务端 JSON ~KB |
| market index 热 cache | < 5 ms | 本地 JSON parse |

CI gate: 加 `cargo bench` benchmark 自动测 daemon RSS / cold start, 超阈值 fail。

## 6. Migration / 兼容

- **既存 ~/.claude.json 用户**: v0.13.x 写的 MCP 条目继续有效, **不动**。新加 / 改的走 shim。
- **既存 ~/.frank/state.json**: 加 `synced_from_remote: bool` 字段 (default false), `frank tenant sync` 拉的标 true。
- **跨机隐私**: `/tenant/skills/report` 服务端验 visibility ∈ {frank-official, frank-recommended}, 用户 community/team/private 一律拒收 (404 + log)。
- **MCP 凭证迁移**: `frank mcp migrate` 一次性扫 `~/.claude.json` 找含 env-with-password 的条目, 提示用户走 shim 重配。不强制。

## 7. 风险 + 缓解

| 风险 | 缓解 |
|---|---|
| daemon 死了 5 通道全挂 | 每个通道 fail back in-process (CLI 现有, hook 加, mcp-shim 必须 fallback) |
| mcp-shim 拖慢 MCP 启动 | shim 必须 < 20ms, 走 frank-cred 内存 cache, exec 用 execvp 不 fork |
| 服务端 index 失效 | 客户端 disk cache 24h TTL 兜底, ETag 304 不增流 |
| 跨机 skill 同步泄漏隐私 | 服务端硬过滤 visibility, 客户端只上报 frank manifest 内的 |
| MCP 配置写崩用户 ~/.claude.json | tmp + rename 原子, 只动单一 entry, 严禁全文 serialize |
