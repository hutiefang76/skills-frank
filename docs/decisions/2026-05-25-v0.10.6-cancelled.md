## 背景

v0.10.6 原计划:`frank install` 后自动 disable 4 provider 的 official mcp_memory(让 frank-memory 接管)。

P 阶段已完成(agent `ae4b369d37bf76934` 出了 GO-WITH-CAVEATS 报告),`PHASE-6-PLAN.md` 已写。

## 用户反馈中的根本质疑

用户审 PLAN 时反问:"你到底在干?如果是记忆需求,我要的是不污染上下文 + token 几乎不消耗 + 本地性能小 + 多机共享(参考 mem0/memorix)。"

## 砍掉理由

**自动接管的目的** = 让 frank-memory **替换** mcp_memory(因为 frank 省 token)。
**但 frank-memory 当前并没真正比 mcp_memory 牛** — 关键差异化在:
- LanceDB 本地缓存(v0.11)
- 多路召回 4 路 + RRF(v0.11)
- 三类记忆 / 三层 session(v0.11)
- 多机同步强化(v0.12)

**现在 disable mcp_memory 让用户用"半成品 frank-memory" = 价值倒挂**。

等 v0.11 把 frank-memory 真正弄牛后,用户**自己会想接管**,根本不需要 frank 强推。

## 影响

- ✅ 不影响 `frank doctor` 现有"记忆系统全景"诊断功能(v0.10.5 已 ship)
- ✅ 不影响用户已用的 mcp_memory(留着继续用)
- ✅ 不影响 frank-memory 现有 CLI(`frank memory add/search/list`)继续可用
- ⚠️ PHASE-6-PLAN.md 留作 v0.12+ 真接管时的设计参考(format-preserving byte-splice + backup 模型仍可复用)

## 替代方案

跳过 v0.10.6,直接进:
1. **v0.10.7** — 你 P0/P1 新需求(多模型动态加载 + 多窗口并发 + history 管理)
2. **v0.11** — 真正让 frank-memory 碾压 mcp_memory(LanceDB 本地 + 多路召回 + 三类记忆 + 三层 session)
3. **v0.12** — 多机同步强化 + Graph + MCP server + device token
